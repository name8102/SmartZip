# 一、最严重的问题：递归解压状态机存在逻辑缺陷

你现在的核心循环：

```rust
while let Some(mut candidate) = queue.pop_front()
```

本质上是一个 BFS 递归解压状态机。

但这里存在几个关键 bug。

---

# Bug 1：`seen` 去重策略错误

当前：

```rust
fn candidate_key(candidate: &ExtractionCandidate) -> String {
    format!(
        "{}:{}:{:?}",
        candidate.path.display(),
        candidate.embedded_offset.unwrap_or(0),
        candidate.source
    )
}
```

问题：

- `path.display()` 不是 canonical path
- Windows 下大小写不敏感
- symlink / `..` / 相对路径会导致重复解压
- extracted path 与 real path 可能不同
- 同一路径不同 recursion context 会误判

这会导致：

- 无限递归
- 重复解压
- 某些 nested archive 被跳过
- queue 爆炸增长

这是非常典型的 archive crawler bug。

---

## 修复建议

改成：

```rust
std::fs::canonicalize()
```

并使用：

```rust
(PathBuf, depth, offset)
```

作为 key。

更好的是：

```rust
#[derive(Hash, Eq, PartialEq)]
struct CandidateIdentity
```

不要用字符串拼接。

---

# Bug 2：recursive extraction depth 判断存在 off-by-one

当前：

```rust
candidate.depth > request.recursion_limit
```

假设：

```rust
recursion_limit = 3
```

实际上：

- depth=0 root
- depth=1 nested
- depth=2 nested
- depth=3 nested

仍然会继续进入处理逻辑。

通常用户理解：

```text
max_depth = 3
```

应该最多处理到 3。

现在的行为更接近：

```text
allow depth <= 3
```

很容易导致：

- 深层 zip bomb
- 多层递归失控

---

## 建议

改成：

```rust
candidate.depth >= request.recursion_limit
```

或者明确文档定义 root 是否计数。

---

# Bug 3：编码检测逻辑 fundamentally 错误

你现在：

```rust
entry.path.as_os_str().as_encoded_bytes()
```

这是严重问题。

---

## 原因

Rust 的：

```rust
OsStr::as_encoded_bytes()
```

不是 archive 内原始 filename bytes。

它是：

> 当前平台编码后的 OS representation

也就是说：

- Linux 下 UTF-8
- Windows 下 WTF-16 转换

你已经丢失了 archive 内真实 bytes。

---

## 后果

你的：

```rust
smartzip_encoding::ArchiveEncodingDetector
```

基本不可能正确工作。

尤其：

- Shift-JIS
- GBK
- CP437
- Big5

都会检测错误。

---

## 正确做法

archive backend 必须返回：

```rust
raw_filename_bytes: Vec<u8>
```

而不是：

```rust
PathBuf
```

编码检测必须基于：

```text
archive metadata 原始字节
```

否则整个“自动编码识别”功能实际上是假的。

这是目前仓库最核心的架构错误之一。

### 🌟 方案中最惊艳的三个亮点 (The "Aha!" Moments)

1. **Artifact-Centric 与 Expansion Stage 独立化**
这是整个方案的灵魂！传统的解压工具总是试图 `extract -> detect -> recurse` 一气呵成，这在遇到嵌套压缩、分卷、多编码混合时必定崩溃。
你引入 `Artifact` 的概念，将“解压产物”和“下一个压缩包的发现源”解耦。这意味着你可以对 `Artifact` 做哈希去重（防止循环解压）、做病毒扫描、做延迟展开（Lazy Expansion，这对于 GUI 树状浏览简直是神器）。
2. **RawArchiveEntry 解决编码痛点**
你敏锐地察觉到了目前 `PathBuf` 和 `String::from_utf8_lossy` 带来的灾难。明确要求 Backend 返回 `Vec<u8>`，然后通过 `EncodingResolver` 统一决策，这是实现跨平台/跨语言字符集（Shift_JIS, GBK 等）完美解压的**唯一正确路径**。
3. **Transaction Extraction (三阶段提交)**
解压到 Temp -> Verify -> Atomic Move。这个设计极其优雅，保证了系统的**幂等性（Idempotency）**。如果系统崩溃或用户取消，目标文件夹永远不会出现“解压了一半的残次品”。这对最终用户的体验提升是巨大的。

### ⚠️ 落地过程中的潜在挑战与避坑指南 (Constructive Critiques)

你的架构宏图已经很完美了，但在 Rust 实际落地时，有几个点需要特别注意：

#### 1. Backend `ArchiveSession` 的实现难点

* **挑战**：你期望 backend 能有 `open once, reuse` 的 Session 能力，以减少 IO 浪费。但如果底层依赖的是 `7z` 的 CLI 进程（`tokio::process::Command`），**CLI 是无状态的**。你很难让一个 `7z` 进程一直活着并接受不同的指令（比如先 `l` 再 `x`）。
* **建议**：
* **方案 A (纯 Rust/FFI)**：逐渐废弃 CLI，引入 Rust 原生库（如 `sevenz-rust`, `zip`）或通过 C bindings 接入 `libarchive` / `7z.dll`。这样可以真正实现内存级的 Session 控制。
* **方案 B (伪 Session/缓存机制)**：如果短期内必须用 CLI，`ArchiveSession` 可以在内部缓存 `list` 的结果。即第一次 `open` 时预读目录树，后续的 `extract` 依然起新进程，但规避了重复探查的开销。



#### 2. TempStorage 的磁盘与 IO 惩罚 (The IO Penalty)

* **挑战**：Transaction Extraction 机制要求先解压到 Temp 目录再 Move。如果一个压缩包有 50GB，临时目录（通常在 C 盘或 `/tmp`）可能会爆满；且跨文件系统/跨分区的 `Atomic Move` 实际上是昂贵的深拷贝（Copy + Delete）。
* **建议**：
* Temp 目录必须建立在**目标输出路径的同级目录**（例如 `target_dir/.smartzip_temp_xxx/`），这样 `commit` 时可以利用文件系统的硬链接或直接重命名（`fs::rename` 达到真正的原子操作 O(1) 开销）。
* 提供一个 `FastPath` 或 `ZeroCopy` 策略开关：对于极大的文件，允许跳过 Temp 阶段直接写入（牺牲安全性换取性能）。



#### 3. DAG 的环路检测与拉链炸弹 (Zip Bomb & Cycle Detection)

* **挑战**：你的 `ArchiveGraph` 是一个动态增长的 DAG。恶意压缩包（42.zip，嵌套了数百万个压缩包）或者包含恶意符号链接（Symlink 指向上一级目录）的压缩包，会导致 `ExpansionQueue` 发生内存溢出（OOM）或无限递归。
* **建议**：
* 在 `ArtifactStore` 或 `Scheduler` 中必须引入 **Content Hash Deduplication** 和 **Depth Limit**。如果一个 `Artifact` 的 Hash 已经被处理过，直接在 Graph 中连线，拒绝重复入队。



#### 4. 级联取消 (Cascading Cancellation)

* **挑战**：基于状态机和队列的设计，如果用户在 GUI 点击了“取消某一个子任务”，或者父节点解压失败，如何干净地清理状态？
* **建议**：
* Rust 的 `tokio::task::JoinHandle` 和 `CancellationToken` 是绝配。建议为每一个 `ArchiveNode` 绑定一个衍生的 `CancellationToken` (Child Token)。父节点取消时，自动 cancel 所有子节点，触发 Cleanup 逻辑。

### T0 阶段：紧急止血热修复 (Hotfixes)

**原则：** 只需要修改几行代码（修复成本极低），但能立刻解决“死锁、崩溃、核心功能完全失效”等致命问题。这些修改不会影响后续的重构，必须**今天**就提 PR 合并。

* **[最高] Bug：`7z` 缺少 stdin 导致进程死锁挂起**
* *影响：* 遇到加密包直接卡死整个程序。
* *修复：* 1 行代码。在 `sevenzz.rs` 的 `Command::new` 链式调用中加上 `.stdin(Stdio::null())`。


* **[极高] Bug：多卷压缩包正则漏洞 (`.part01.rar` 被跳过)**
* *影响：* 包含前导零的大型分卷包被静默丢弃，永远不解压。
* *修复：* 修改 `is_first_volume` 的匹配逻辑（1 行正则或逻辑判断）。


* **[高] Bug：手动指定编码被静默丢弃 & 底层未传参**
* *影响：* CLI 传了 `--encoding GBK` 依然乱码。
* *修复：*
1. 修复 engine 中的 `unwrap_or(EncodingMode::Auto)` 覆盖逻辑。
2. 在 `sevenzz.rs` 中提取 `encoding` 字段，并根据值补充 `-mcp={CodePage}` 参数传给 7z 进程。




* **[中] Bug：非密码错误导致正确密码被降权**
* *影响：* 长期运行会导致用户的本地密码库被污染，好密码排名垫底。
* *修复：* 在 `extract_recursive` 的 `Err(error)` 分支里加个判断，只有 `matches!(error, SmartZipError::WrongPassword)` 才调用 `record_failure`。



---

### T1 阶段：核心拓扑与数据结构重构 (Phase 1)

**原则：** 解决由“旧模型设计缺陷”导致的系统性深水区 Bug。这一步是重构的基石，主要引入 `Artifact` 和 `ArchiveNode`。

* **架构动作：** 剥离 Expansion 阶段，引入 `RawArchiveEntry` 和 `Artifact` 实体。
* **一并解决的 Bug：**
* **Bug：`from_utf8_lossy` 彻底破坏自动编码检测**
* *为何在此修复：* 修复它需要修改 Backend 接口，让它返回原生的 `Vec<u8>` 而不是被转义过的 `String` 或 `PathBuf`。在引入 `RawArchiveEntry` 时顺手解决。


* **Bug：`seen` 队列基于 `.display()` 去重导致的无限递归**
* *为何在此修复：* 新架构将使用 `ArtifactId` (基于 Content Hash 或规范化路径) 替代脆弱的字符串拼接，从根本上消灭路径误判。


* **Bug：Scanner 层层扫描导致 $O(n^2)$ 的 IO 风暴**
* *为何在此修复：* 新架构中，解压产生 `Artifact` 后，只会对新增的 `Artifact` 触发一次 ExpansionTask，天然杜绝了重复扫描整个父文件的行为。


* **Bug：递归深度判定 (Off-by-one) 越界**
* *为何在此修复：* 将深度控制从 `while` 循环剥离，交给新的 Pipeline 状态机管理，逻辑自然理顺。





---

### T2 阶段：执行器与异步安全 (Phase 2)

**原则：** 解决 Tokio 异步环境下的资源调度、并发安全和失控风险。引入 `Scheduler` 调度大脑。

* **架构动作：** 引入 `TaskQueue`、资源感知调度 (Resource-Aware Scheduler) 和 `CancellationToken`。
* **一并解决的 Bug：**
* **Bug：Async 运行时内部夹杂 Sync IO 导致线程池阻塞**
* *为何在此修复：* 引入 Worker Pool 时，必须全面梳理 IO，将 `std::fs` 彻底替换为 `tokio::fs` 或放入 `spawn_blocking`。


* **Bug：没有 Cancellation 机制，GUI 无法取消大型任务**
* *为何在此修复：* 新的 Scheduler 会为每个 `ArchiveNode` 颁发衍生的 CancellationToken，实现级联取消（一键杀停所有相关进程和子任务）。


* **Bug：缺乏解压上限，易受 Zip Bomb (42.zip) 攻击**
* *为何在此修复：* Scheduler 内部引入 PolicyEngine，统一拦截校验“最大文件数、最大解压体积、最大深度”，超出立刻阻断。





---

### T3 阶段：IO 安全与策略层完善 (Phase 3)

**原则：** 收尾高风险的 IO 操作和体验一致性问题。此时系统底座已经非常稳固。

* **架构动作：** 引入 `MaterializationMode` (三阶段事务解压)、完善 `PasswordResolver` 责任链。
* **一并解决的 Bug：**
* **Bug：`collapse_single_output` 中的跨盘符 Rename (EXDEV) 崩溃风险**
* *为何在此修复：* 事务解压机制会统一管理 Temp 目录。通过将 Temp 与目标目录保持同盘，并在 Commit 阶段使用原子重命名 (Atomic Rename) 或回退到 Copy+Delete，彻底消灭 IO 异常。


* **Bug：Interactive 密码流没有走 test 导致误判**
* *为何在此修复：* 独立的 `PasswordResolver` 将统一密码校验接口。所有密码验证（不管是字典跑出来的还是手敲的）都会被强制通过 `ArchiveSession::test()` 进行一致性校验。


* **Bug：错误处理吞噬 (`let _ =`) 导致静默失败**
* *为何在此修复：* 结合 EventBus 的引入，所有不可恢复的 Error 都会转化为 `ArchiveFailed` 事件抛给前端，日志和错误传播链将变得严密。
