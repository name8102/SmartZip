# Fix Plan Design

## Objective

在不先读实际代码的前提下，先把当前已知程序问题整理成一份可执行的修复规划：明确问题列表、排查顺序、修复阶段和非目标，为后续真正进入代码排查提供统一入口。

## Planning Boundary

- 本任务当前阶段只基于：
  - 已迁移的旧需求/设计/计划/进度文档
  - 用户已经确认的程序问题现象
- 本任务当前阶段不做：
  - 实际代码阅读
  - 根因确认
  - 测试复现
  - 代码修复

这意味着本任务输出的是“排查与修复路线设计”，不是“根因结论”。

## Core Structure

规划结果分三层组织：

1. 问题列表
   - 把已确认的现象按优先级和类别归档
   - 区分 P0 主流程问题与 P1 能力边界/体验问题
2. 排查顺序
   - 先排核心解压主流程
   - 再排输出与 CLI 契约
   - 最后排编码、后端边界和长期结构
3. 修复阶段
   - 将后续实施拆成 Phase 0 到 Phase 5，保证顺序收敛

## Ordering Rationale

排序原则不是“最容易改”，而是“最影响当前可交付能力”：

- 第一优先级：核心解压是否可用
  - 分卷
  - 密码
  - 批量/嵌套
- 第二优先级：解压成功后是否符合预期
  - 目标路径
  - 覆盖/删除
  - 部分成功语义
- 第三优先级：用户是否能理解和控制流程
  - CLI 多输入交互
  - 错误提示
  - 退出码
- 第四优先级：能力边界与技术路线是否清晰
  - ZIP 编码
  - 原生 ZIP 与 7z fallback 的职责
  - 外部依赖策略

## Deliverables

本任务应产出：

- 一份按优先级排序的问题列表
- 一份不读代码前提下的排查顺序
- 一份大致修复阶段计划
- 一份明确的 deferred work 列表，防止 GUI/打包等后置事项混入当前主线

## Risks

- 不读代码的规划会保留不确定性，因此必须把“待验证”与“已确认现象”分开。
- 如果过早把后端、编码或 GUI 结构问题提到前面，会稀释当前“核心解压可用”主线。
- 如果不把目标路径、覆盖、删除单独列为一类，后续容易被误并入“解压成功率”而遗漏。
