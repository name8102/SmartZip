# Fix Plan

## Goal

将问题清单转化为分阶段、可验证、可排序的修复路线，作为后续实际开发任务的直接输入。

本任务建立在“旧计划先迁入 Trellis，再按现实重排优先级”的前提上。旧 `docs/implementation-plan.md` 提供的是历史阶段结构，不是当前可直接执行的路线。

## Confirmed Facts

- `docs/implementation-plan.md` 已提供一版历史阶段路线，可作为输入但不能直接照搬。
- 当前近期目标不是整体平台重写，而是先恢复核心功能可靠性与 CLI 可用性。
- 修复路线需要覆盖真实缺陷修复、测试回归、安全边界和后续能力建设之间的优先级。
- `docs/implementation-progress.md` 中的“已完成”阶段会影响优先级判断，因此修复路线必须显式处理这些历史声明与当前现实之间的落差。
- `06-27-core-investigation` 已被定义为前置调查任务；修复路线必须吸收其中的复现条件、代码路径、初步根因和验证建议。
- 当前关于 ZIP 路径的新决策已经确认：
  - 原生 ZIP 后端暂时不再承担复杂 ZIP 解压主路径。
  - ZIP 的 `probe/list/test/extract` 近期优先走 `7z` / `7zz`。
  - 全自动 ZIP 编码检测延后，不再作为当前阶段的默认可用能力。
  - 作为替代，CLI 需要补一个“多编码文件名预览”辅助命令，帮助用户选择正确编码。

## Requirements

- 修复计划必须优先处理当前真实缺陷：
  - 解压失败
  - 分卷失败
  - 正确密码仍失败
  - ZIP 编码相关行为错误
  - 批量/嵌套解压流程不稳
  - CLI 多输入交互混乱
  - 文件操作和目标路径行为不符设计
  - 环境依赖/后端定位不匹配
  - 已复现的失败测试
- 修复计划必须先承接旧计划中仍有效的阶段意图，再重排优先级；不能完全抛开旧路线另写一套无来源的新阶段。
- 修复计划的排序依据必须同时包含：
  - 旧计划中仍有效的阶段结构
  - 当前调查任务确认的真实失败路径和阻塞程度
- 修复计划必须分阶段组织，至少区分：
  - 当前行为错误修复
  - 可靠性/安全性收敛
  - 格式能力补强
  - 密码策略完善
  - 后续结构演进
- 每个阶段都要写明：
  - 目标
  - 依赖前提
  - 非目标
  - 验证方式
- 修复计划应显式说明哪些历史设计项本轮不做，例如 GUI 事件流、完整工作台、发布集成。

## Migrated Phase Intent

从旧 `docs/implementation-plan.md` 迁移后，仍然保留的阶段意图如下：

- 先收敛真实行为错误，而不是先做 GUI 或平台集成。
- 后端边界、密码策略、输出安全和递归工作流需要分阶段推进，不能在单一“智能解压已完成”的口径下被掩盖。
- 编码、分卷、密码、嵌套这些能力之间存在耦合，修复路线必须允许先拆分验证，再合并回主流程。

以下旧阶段意图降级：

- GUI 原型、GUI 工作台、打包发布，不再作为近期 P0/P1。
- 任何把“命令存在”直接等价为“能力可用”的阶段结论，全部降级为历史记录。

### Phase 0: 复现并收敛当前故障

- 收集失败样本，最少覆盖：
  - 一个分卷包
  - 一个正确密码仍失败的加密包
  - 一个乱码 ZIP 文件名样本
  - 一个批量多输入交互混乱样本
  - 一个目标路径/覆盖/删除行为不符设计的样本
- 先确认哪些问题可稳定复现，避免按历史笔记盲修。
- 输出每个样本对应的后端路径、错误类型和 CLI 行为。
- 对照旧 `implementation-progress` 的完成声明，标记哪些属于“代码路径存在但不可视为功能完成”。
- 当前补充结论
  - multipart 样本和端到端回归仍缺失，必须补齐后再把“分卷已支持”纳入当前事实。
  - 高 CRAP 项不是纯复杂度噪声；在进入 Phase 1 前，至少要先补最小回归护栏，覆盖：
    - 错误密码必须形成明确失败事件/输出
    - `nested_multi_level.zip` 递归到最深层时不能出现路径冲突
    - CLI 的 `--json`、默认 DB 行为、`password export` 默认路径契约
  - 对 ZIP 路径，当前“先恢复可用性”优先于“保留 Native ZIP 架构目标”；因此 Phase 1 可以接受先把解压主路径切到 7z，再在后续阶段重新评估原生 ZIP 方案。

### Phase 1: 修正当前行为错误

- 目标
  - 修复可稳定复现的解压失败、分卷失败、密码正确仍失败、外部命令定位不清晰等问题。
  - 先恢复“核心解压能力可用”的最低可交付线。
- 当前优先纳入
  - 多层嵌套解压中的 `File exists` 输出冲突
  - 错误密码被静默吞掉、无法形成明确失败结果
  - multipart 真实样本补齐后复现出来的首卷提取失败
  - ZIP 路由切换后仍存在的“误报成功解压”问题
  - 与以上缺陷直接绑定的最小回归测试补齐
- 本阶段完成口径
  - 以“核心解压成功率恢复”为准，不把目标路径、覆盖、删除等落盘契约一并并入 Phase 1 完成条件。
- 依赖
  - Phase 0 已给出最小复现样本。
- 非目标
  - 不在本阶段推进 GUI、事件流、完整平台集成。
  - 不要求在本阶段同时收敛目标路径选择、覆盖策略、删除策略。
- 验证
  - 对应 fixture 的集成测试或 CLI 手工验证。
  - 修复对应的高 CRAP 项后重新跑 `./scripts/crap-scan.sh --top 5`，确认风险项要么下降，要么已有明确的覆盖提升解释。

### Phase 2: 收敛可靠性与 CLI 契约

- 目标
  - 明确退出码、错误分类、日志/提示、分卷与密码失败的用户可见行为。
  - 收敛批量多输入、密码补输、目标路径选择、覆盖/删除确认等 CLI 契约。
  - 核实当前 layout / materialize / collision 行为是否真正满足迁入的需求基线。
- 本阶段承接
  - 处理 Phase 1 明确后置的目标路径、覆盖、删除和其他落盘契约问题。
  - 明确“手工密码”和“数据库密码候选”的优先级/覆盖语义。
  - 处理默认数据库路径与帮助文案、环境假设之间的不一致。
  - 处理已公开但未兑现的 CLI 接口，例如 `extract --json`。
  - 统一密码导出默认路径与平台路径约定。
- 依赖
  - Phase 1 修复完成。
- 非目标
  - 不扩展新的大能力面。
- 验证
  - `smartzip extract` / `detect` 的命令行为验证。

### Phase 3: ZIP 编码与后端边界澄清

- 目标
  - 固定“当前 ZIP 主路径由 7z 承担解压”后的能力边界。
  - 明确“当前编码处理并不等于自动编码检测可用”，避免再把部分代码路径误记为完成能力。
  - 落地“多编码文件名预览”命令，作为自动检测延后的替代交互。
- 依赖
  - 已有乱码样本和对应测试。
- 非目标
  - 不在本阶段恢复 Native ZIP 为复杂 ZIP 默认主路径。
  - 不把全部格式都纳入统一编码检测模型。
- 验证
  - 编码相关集成测试、样本提取结果以及预览命令输出。

### Phase 4: 后续能力建设

- 目标
  - 处理结构演进项，例如更完整的密码策略、深度模式、动态节点、事件流。
- 说明
  - 这些能力只在前面阶段稳定后再立新任务推进。

### Phase 5: 长期结构与产品面恢复

- 目标
  - 在核心解压与 CLI 契约稳定后，再恢复压缩、预览、GUI、系统集成等长期方向。
- 说明
  - 这些项目已经完成迁移，但不参与当前修复路径排序。

## Current Evidence To Carry Forward

- `SevenZipLocator` 已支持 `7zz` 和 `7z` 双候选；本机仅检测到 `7z`。
- `UnrarLocator` 当前依赖 `unrar`，本机可用。
- 原生 ZIP 库目前无法同时满足分卷、密码、编码和行为一致性要求；短期内不再作为复杂 ZIP 主解压后端。
- `test_engine_respects_recursion_limit` 当前单独运行通过，不应作为当前 P0 缺陷默认纳入。
- 代码中已存在显式编码 override 相关测试，说明编码路径已有部分实现，当前重点应先查“失效场景”和边界错误。
- 自动 ZIP 编码检测暂时降级为后续能力建设，当前更现实的替代是提供多编码文件名预览入口。
- 旧进度文档把若干流程写成“已完成”，但当前用户反馈说明这些描述最多只能视为阶段性实现记录，不足以替代当前行为验证。
- 在 `core-investigation` 输出落定前，本计划中的阶段排序仍属于“待调查确认后的初版路线”。
- `smartzip-engine` 与 `smartzip-archive` 现有已覆盖测试基本通过，说明当前主要风险集中在 CLI 契约、嵌套输出布局和缺失的 multipart 真实回归，而不是这些已覆盖 fixture 本身。
- `smartzip-engine` 的现有测试对高风险函数仍有明显浅断言问题：错误密码场景只断言 `skipped`，多层嵌套场景只断言 recursion limit，没有覆盖真实失败契约。
- `smartzip-cli` 最高 CRAP 函数当前几乎没有测试承接，`extract`、`open_db`、`password` 的风险应视为“实现缺陷 + 覆盖缺失”的组合，而不是单纯测试债。
- 真实 CLI 调查已确认：
  - 错误密码在空数据库场景下会静默变成 `skipped`
  - 数据库中的正确密码会掩盖用户手工输错密码
  - `nested_multi_level.zip` 在 depth 2 会出现 `File exists` 型输出冲突
  - 默认数据库路径行为与代码注释不一致
  - `extract --json` 参数当前公开但未生效
  - `password export` 默认路径未使用平台层导出约定
- multipart 仍未完成真实复现，当前只有“首卷命名识别/非首卷跳过”级别测试，不足以视为能力完成。
