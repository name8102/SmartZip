# Core Investigation Design

## Objective

为实际排查工作建立统一方法，保证调查结果能直接支撑后续修复，而不是再次陷入只凭印象讨论问题。

## Investigation Method

每个问题按同一结构排查：

1. 复现
   - 找到最小样本、命令或操作路径
2. 定位
   - 确认涉及模块、后端、工作流阶段和错误分支
3. 对照
   - 把当前行为与需求基线、修复计划中的预期行为逐项对比
4. 归因
   - 判断是实现缺陷、状态机问题、后端边界问题、CLI 契约问题还是文档边界问题
5. 输出
   - 给出修复建议、验证建议和风险

## Investigation Order

### First Wave: 主流程可用性

- 分卷
- 密码
- 批量/嵌套

理由：
这些问题决定 `extract` 是否还能作为主入口使用。

### Second Wave: 落盘与后处理

- 目标路径
- 覆盖策略
- 删除策略

理由：
即使解压成功，如果落盘结果不符合设计，仍不能算“核心解压能力可用”。

### Third Wave: CLI 契约

- 多输入交互
- 错误提示
- 退出码

理由：
这是“CLI 可用”的必要条件，但排在主流程和落盘正确性之后。

### Fourth Wave: 能力边界与技术路线

- ZIP 编码
- 原生 ZIP 后端
- 7z / unrar fallback
- 环境依赖假设

理由：
这些问题需要结合前面主流程结果来看，否则容易脱离实际症状空谈结构。

## Evidence Sources

- 代码路径
- 现有测试
- fixture / 样本
- CLI 命令行为
- 旧文档迁移后的需求/计划基线

## Deliverables

- 每一类问题的调查记录
- 初步根因与修复建议
- 是否需要拆分后续修复子任务的建议

## Risks

- 如果没有稳定样本，调查会停留在推断层，必须显式标记。
- 如果跳过主流程直接看结构问题，容易误判优先级。
- 如果不把“设计问题”和“实现问题”分开，后续修复会继续混乱。
