# 多输入解压被批量扫描推迟

用户报告多文件解压持续读盘却不写入。定位到两个调度行为：

- 有状态路径用 join_all 一次激活全部根输入，每个输入先做完整扫描。
  同一 I/O 域容量为 1；阶段轮换使全批次扫描排在后续解压前。
- 无状态路径把当前根扫描发现的归档 push_back 到全部后续输入之后。

修复：
- 有状态路径改为 buffer_unordered(2)，最多两个活跃根工作流，任一完成就
  补入后续输入，不被第一个等待交互的根阻止补入。结果按原始输入索引汇总。
  此值匹配现有默认一个后端进程的使用场景，保留另一路准备/交互。
- 当前根扫描产生的归档按发现顺序放到队首，先提取当前输入的结果。
  普通嵌套发现 BFS、跨任务资源调度、全文件根扫描和分卷去重保持原行为。

验证：
- 新增回归测试先在旧实现失败：8 个根全部进入 ScanEmbedded 才开始首次
  密码/解压尝试（observed=8）。修复后断言 <=2，通过且输出结果顺序保持。
- 无状态 8 个内嵌载体测试：第一个解压尝试前只发现当前载体，通过。
- 停止失败任务测试扩为 4 输入，覆盖尚未激活的排队根：1 failed、3 skipped，
  不继续调用后端。已有扫描取消、交互等待、累计预算和分卷去重测试通过。
- cargo test -p smartzip-engine -p smartzip-cli 全部通过；engine 单测
  234 passed / 1 ignored，真实集成 smartzip_integration 69 passed。
  扩充的停止/顺序断言随后分别重跑通过。
- 真实 CLI/7z 到 NFS：8 个各含 8MiB 稀疏前缀和 ZIP 载荷的 .bin，使用互不
  相似的文件名避免分卷归组。通过 strace read/pread64/write 的路径归因，
  第一次 payload.txt 写入前，有状态只有前 2 个输入发生大量读取，无状态
  只有第 1 个；所有 8 份输出内容核对成功。原始读量见 validation.json。
