# 已解压任务优先收尾与 I/O 调度

## 原因

- `ExecutionCoordinator::transition` 先释放原阶段并立即派发其他任务，再等待数据库写入、申请后续阶段。刚提取完成的任务因此会被其他长时间扫描/解压占用设备资源。
- 调度只按累计服务量与任务权重排序，已消耗较多服务量的任务在提交阶段仍落后于新扫描。
- InspectAndPlan、AnalyzeEncoding 未占用前后阶段使用的 I/O 域，即使增加优先级，其他扫描也能在短阶段之间插入。
- 默认全局后端进程数为 1，导致互不共用设备的任务也无法并行解压。

## 实现

- 在等待阶段状态持久化时保留旧租约，在同一锁内释放旧租约、排入后继阶段并调度；状态写入失败或过期时释放资源。
- 排序优先级：检查/提交/子项发现/清理、已准备好的解压、访问准备/编码/元数据、新输入扫描。同级保留加权服务量与队列顺序；不可准入的候选不会阻塞其他根或设备。
- 编码自动确认阶段维持源设备准入，检查和清理维持目标设备准入；用户交互等待继续释放资源，暂停、取消逻辑保留。
- 默认后端进程上限改为可用 CPU 数，同设备 I/O 容量仍为 1；不同设备可以同时运行后端。单批次两个活跃根的窗口保持，避免再次全部预读。
- 不抢占已运行后端；优先级作用于阶段边界。100% 的后端提取进度并不代表递归扫描或整个批次已经完成。

## 验证

- 先新增运行时回归测试，旧实现稳定触发超时：第二个解压排队时，第一个无法进入 InspectAndPlan。修改后通过。
- 覆盖单核、多核、同任务多根和跨任务收尾；扫描完成后连续准备/编码/提取；累积服务量较高的已准备输入优先于新扫描；受阻提交不妨碍另一设备扫描；多核 host 配置允许两个独立设备同时运行后端。
- 独立设备用测试 I/O 域模拟，不依赖 CI 挂载多块硬盘，不将准入测试当作吞吐性能证据。
- `cargo test -p smartzip-engine -p smartzip-gui -p smartzip-cli`：398 passed，7 ignored，0 failed。原多输入、防饿死、交互释放、取消和恢复用例通过。
- `cargo test -p smartzip-gui --test runtime_worker -- --include-ignored`：12 passed，包含真实后端和数据库任务。
- CLI/GUI debug 构建通过；未替换系统安装程序，未做原生 GUI 点击或磁盘吞吐基准。

## NFS 子项发现后续

- 运行中批次显示单个 `DiscoverChildren` 长时间占用 NFS I/O 域，后续根停在
  `waiting_resources`。历史同输入批次也由该阶段主导，因此根因不是任务中心
  渲染，而是解压后预算清点与递归发现连续两次遍历发布树，再被单许可设备域
  放大为队头阻塞。
- 最终预算清点现在保留普通文件的暂存区相对路径，并按 `LayoutPlan` 映射到
  最终发布目录。正常解压直接用这份 inventory 做子项发现；恢复路径缺少内存
  inventory 时仍保留安全的文件树重扫回退。
- ZIP 业务容器结构分类从发现阶段移到已确认 ZIP 的嵌套子节点阶段。显式
  `.docx/.xlsx/.pptx/.epub/.apk/.jar` 仍按后缀立即排除；普通 ZIP 不再发现、
  执行各遍历一次中央目录。
- 小文件阈值只用于无归档后缀的内容探测：低于阈值的 `.bin/.jpg` 等不读取
  文件头或做深度扫描；具有归档后缀的文件不受该阈值影响，仍读取头部并进入
  后续解压判断。inventory 同时保留文件大小，避免为该判断再次访问 NFS 元数据。
- 每个 I/O 域默认容量从 1 调整为 2。单批次活跃根窗口仍为 2，输出路径租约
  继续串行化冲突提交，因此同一设备可重叠两个解压，或重叠子项发现与下一根
  解压，而不会并发发布同一输出命名空间。
- `cargo test -p smartzip-engine`：345 passed，1 ignored，0 failed；
  `cargo test -p smartzip-gui`：54 passed，7 ignored，0 failed；
  `cargo check --workspace` 和 `git diff --check` 通过。未中断运行中的旧进程，
  新实现尚未做真实 NFS 吞吐复测。
